# Agent 交接 / Handoff 模板与纪律

> 用途：任务跨会话、跨 agent 移交时。
> 价值：一份好的 handoff 能省掉接手方整轮重新盘点。

## 何时写

- 任务未完成但必须停（上下文将满、要重启、要换 agent）
- 任务分阶段，每阶段收口
- 从本机任务交给另一个 agent

## 模板

```markdown
# <任务名> Handoff

> 生成时间：YYYY-MM-DD HH:mm（含时区）
> 生成 agent：<名字 + 模型>
> 工作区（cwd）：<绝对路径>

## 1. 背景与目标
这个任务要达成什么，为什么要做。

## 2. 当前状态
已完成 / 进行中 / 未开始，各带证据路径。

## 3. 已确认的事实
带证据级别；关键数字写清算过。

## 4. 未决事项
按优先级排序，每条写"卡在谁"。

## 5. 已尝试过且失败的方案
免得接手的人重蹈覆辙；写清失败特征，不只写"不行"。

## 6. 下一步（最短安全路径）
具体到命令级别；标注哪些要先问人。

## 7. 不要动的东西
红线清单 + 原因。

## 8. 证据与产物索引
文件路径列表，每条一句话说明。

## 9. 已知坑
环境坑、工具坑、权限坑——单独一节，最容易忘也最有用。
```

## 五条纪律

1. **交接文档是历史信息，不是新的授权。** 接手方仍要按现场状态重新验证。
2. **不要把"未验证"写成"已验证"**——会被逐条核对，一条就够毁掉信任。
3. **失败方案必须写。** 这是 handoff 最有价值的部分，比成功步骤重要。
4. **路径用绝对路径**，会话引用带 ID。
5. **格式可读性也要检查**——曾出现过 handoff 全文被反斜杠转义破坏、渲染失效的情况。

## 接手方要做的

1. 先读 §2 状态与 §5 失败方案。
2. **重新验证现场状态**再动手，不要直接续。
3. handoff 与现场不符时，**先报告差异**再继续。
4. 完成后更新 handoff 状态或归档，不要留悬空文档。

## 一个常见失败模式

**"继续上个会话"这类指令几乎不带信息。**

它假设接手方知道"上个会话"是什么、进行到哪、目标是什么。如果没写 handoff，
接手方只能靠翻会话历史重建上下文——慢，且容易翻出过期结论。

> 结论：**handoff 不是额外开销，是让"继续"这个词变得可用的前提。**
