# 多层记忆栈：归属、权威源、防竞争副本

> 用途：设计或维护"多个 agent 共享知识"的设施时。
> 核心问题：**同一个事实不该有两处权威源。**

## 问题：多套记忆并存必然漂移

一旦同时用多个 agent，每套工具都会自带记忆系统，很快就会出现六七个存储：

```text
A 的自有记忆（某 agent 的任务摘要）
B 的自有记忆（另一个 agent 的）
云盘里的手工笔记
某个知识图谱工具
某个向量数据库
项目目录里的 STATUS.md
...
```

漂移是必然的，不是意外。**真实案例**：一次全机盘点发现某条身份信息在各套记忆里有互相矛盾的版本，
而没人知道哪个是最新的——因为每套都能被独立写入，且都没有"我是权威"的标记。

## 分层原则

按"内容类型"分层，而不是按"agent"分层：

| 层 | 放什么 | 形态 | 是否权威源 |
| --- | --- | --- | --- |
| 档案层 | 身份、偏好、工作流 | 纯文本 + git | **是** |
| 规则层 | 硬性红线、环境约定 | 手工维护的少量文件 | **是** |
| 共享记忆层 | 跨 agent 的键值事实 | SQLite + MCP | **是** |
| 任务记忆层 | 某项目的细节与失败教训 | 各 agent 自有 | 项目细节的权威源 |
| 索引层 | 扫描生成的知识图谱 | SQLite | **否，可重建** |
| 镜像层 | 给人看的网页/双链笔记 | 生成产物 | **否，可覆盖** |

## 五条硬规则

1. **写入前先确认归属。** 这条内容属于哪一层？该层已有权威源吗？
2. **不制造竞争性副本。** 同一事实只在一处是权威；其余只做派生。
3. **变更走 supersede，不改 key。** 保留审计链，让"这个结论什么时候变成这样的"可查。
4. **可重建的层禁止手改。** 索引和镜像层是产物，改了下次扫描就丢，还会掩盖"源数据有问题"。
5. **定期做一致性核对。** 每季度一次，重点看身份类、数字类、日期敏感类。

## 防竞争副本的具体机制

在共享记忆层用一条数据库约束就能挡住大部分问题：

> **同一个 `memory_key` 已有 active 条目时，`add` 操作直接拒绝，必须走 `supersede`。**

这把"悄悄新建一条矛盾的"变成了"必须显式替换旧的"，替换时还会强制留下原因。

## 一个反直觉的发现

**"丢失"有时只是"从未在新环境生成过"。**

盘记忆栈时发现某层整个不见了，第一反应是"被删了"。实际查证：
那层是**生成产物**，只在旧机器上跑过一次生成器，新机器从未跑过——目录是空的，不是被清空的。

**教训**：看到层缺失，先判断它是"源数据"还是"生成产物"。
生成产物缺失只要重跑生成器；源数据缺失才需要走恢复流程。

## 自检清单

- [ ] 这条内容属于哪一层？
- [ ] 该层已有权威源吗？有的话我在制造副本吗？
- [ ] 如果是更正，我走的是 supersede 并留下原因吗？
- [ ] 我有没有手改某个可重建的层？
- [ ] 这次一致性核对是什么时候做的？
